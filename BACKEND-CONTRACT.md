# Java backend integration contract

- Java 17; RuoYi 3.9.2; Spring Boot 3.5.16, pinned by the upstream parent POM. Build from this directory using `mvn -B -ntp verify`.
- The current project contains the Java backend and `admin-ui` only. The legacy Node backend, its Vue frontend and root-level Node entry points have been removed. Node.js/npm remain frontend development/build tools; Java compilation, tests and runtime do not require the deleted application.
- `ruoyi-admin` is the executable Spring Boot entry point. It loads `ruoyi-warehouse`, which depends on `ruoyi-common`, Spring JDBC and Jackson. Tests use the Spring Boot test starter and JUnit 5 through Surefire 3.5.3.
- Warehouse packages live under `com.ruoyi.warehouse`; component scan and `com.ruoyi.**.mapper` scanning already cover the module. Mapper XML belongs under `src/main/resources/mapper/warehouse`.
- `/warehouse/**` always requires the existing RuoYi JWT authentication, including paths marked anonymous by mistake. Native controllers must also apply `@PreAuthorize("@ss.hasPermi('warehouse:<resource>:<action>')")`. Authentication alone is not a business authorization policy.
- Read the authenticated account using `SecurityUtils.getLoginUser()` / `getUserId()` from `ruoyi-common`. Return `AjaxResult` or `TableDataInfo` through `BaseController`, consistent with the RuoYi frontend. Preserve RuoYi superadministrator behavior.
- Client and warehouse scope use explicit `wh_user_scope` grants owned by the business module, not `sys_dept` data scopes. Non-admin access without grants must fail closed. User-supplied query/body IDs do not grant scope. Every list, detail, mutation, export, bulk operation and related-row lookup needs the same scope enforcement.
- Native business APIs include `/warehouse/catalog`, `/warehouse/records/{kind}/list`, `/warehouse/records/{kind}/{id}`, `/warehouse/inventory`, `/warehouse/orders` and `/warehouse/security/scopes/{userId}`. The schema is supplied by numbered `sql/warehouse_*.sql` migrations. The scope GET returns an opaque `_version`; PUT requires that version and both `clients` and `warehouses` arrays. An empty array means no access, not unrestricted access.
- Generic master writes are limited to clients, products, warehouses, location types, locations, suppliers and channels, with administrator restrictions on shared catalogs. Workflow records must use their own transactional services. The catalog deliberately retains read-only entries for business modules that have not migrated yet; it is not a completion manifest.
- Warehouse business validation failures (400/403/404/409) and transaction concurrency rollbacks include `data.committed=false`. An unknown transport or server outcome must retain the original request ID and payload for replay; it must not create a replacement request. In particular, a later permission denial cannot prove an earlier timed-out request did not commit.

## ASN receiving

- `/warehouse/inbound/list` and `/{id}` require `warehouse:asns:list` / `query`. POST creates a forecast; PUT `/{id}` revises an unreceived forecast. POST `/{id}/receive`, `/close` and `/cancel` each require their named `warehouse:asns:*` permission. Generic master writes remain disabled for `asns`.
- All writes require `requestId`; edits and actions also require `_version`. Same-actor replay checks current ASN scope before returning the stored result. A reused nonce with different content fails. Receipts, stock layers, ledger, price evidence, fees, audit and nonce commit together.
- `JAVA_ASN_V1` transitions from NEW to PARTIALLY_RECEIVED / RECEIVED, then CLOSED. CANCELLED is only available before receiving. Client/warehouse are immutable; forecast products must be unique, active physical products owned by the client. At most 200 forecast/receipt lines per request, 250 receipts and 2000 receipt lines per ASN.
- Direct receiving puts each line into an explicitly selected normal location, with capacity, ownership, tracking, serial uniqueness and over-receipt checks. Pending custody tasks block this shortcut. Quarantined, damaged, expired and excess forecast products use the dedicated custody workflow below; unexpected/unidentified products remain blocked.
- Unit fees apply per receipt; SKU fees apply once per ASN. Explicit zero is permitted; missing rates fail. Closing confirms actual delivery type/count and labour hours and charges fixed fees once. Shortfall closure requires the real superadministrator, explicit approval and a reason; it does not increase received stock. Client currency changes block receipt/closure.
- Operational responses omit rate snapshots and charge amounts. Charges and immutable calculation evidence use the existing finance path. Customer quotes and real invoices still need validation before production adoption.

### ASN custody and putaway

- Apply `warehouse_019_asn_custody.sql` and `warehouse_020_asn_custody_menu.sql` before starting this version. The new event document uses LONGTEXT with enforced JSON validity and is included in the startup guard. No roles receive automatic grants.
- POST `/warehouse/inbound/{id}/custody/{action}` requires `warehouse:asns:{action}`. Actions are `stage`, `inspect`, `approveOverage`, `putaway`, `scrap`; all require `requestId`, `_version`, and a nonblank `reason` (max 500 characters). Scope and action permission apply before replay; ASN revision serializes all competing tasks. The original forecast is never rewritten by overage approval.
- `stage` accepts one forecast `product`, `location`, positive integral `quantity`, optional `batch`, `serial`, `expiry`. Use a dedicated active Quarantine location with `custodyOnly`; batches, serial uniqueness, product tracking, client/warehouse ownership, freezes and physical capacity are enforced. Expired goods may be held but never put away as saleable inbound stock. Staging adds real unavailable stock, creates its origin/age, and does not assess goods-in unit/SKU charges. It is allowed after full receipt while the ASN remains open, but not after closure.
- `inspect` accepts `task` and `result: PASS|FAIL`. Inspection cannot change after putaway or scrap, or while an unused supplier-return approval exists. A supplier handover alone does not prevent inspecting the remaining held units after all approvals are consumed or cancelled. Reinspection clears unused excess approval. Receive mixed quality as separate tasks. `approveOverage` approves the passed task's remaining physical units for acceptance beyond the forecast if necessary; it neither moves stock nor charges fees. Its unused allowance is bounded by remaining physical quantity and is reduced when consumed. This permission is distinct from receipt, inspection and putaway permissions.
- `putaway` accepts `task`, `quantity`, normal destination `location`. Only PASS stock can move; any actual quantity above the remaining forecast needs this task's approval. Exact custody-layer quantity, age, attributes and lack of reservations must reconcile. Source and destination inventory, source-preserving layers, ledger, receipt, original unit/SKU pricing, audit and request journal share one transaction, including storage-history capture. Missing rates, frozen/full locations or changed evidence roll back everything. SKU fees remain once per ASN across direct and staged receipts. Rates apply at acceptance; no unconfigured quarantine inspection/scrap fee is invented.
- `scrap` accepts `task` and `quantity`, requires FAIL, and removes only the proven custody layer. It produces no accepted stock or goods-in unit charge. Partial disposition is allowed. A fully rejected arrival may be short-closed by the administrator after all custody is resolved; explicitly confirmed delivery/labour and admin fees still apply under the existing closure rules.
- Editing/cancelling a forecast is blocked after any custody arrival, even after disposal. Pending custody blocks closure. Accepted overage is shown separately from nonnegative shortfall. `custodyTasks` and immutable `custodyEvents` expose physical evidence without prices; `custodyPending` gives list-level outstanding physical units. Per ASN: max 2000 custody tasks, 10000000 staged units, 4000 custody events; existing 250 accepted receipts / 2000 receipt-line limits still apply.
- Not covered yet: appointments, unidentified/unexpected SKU identification, supplier returns, post-closure supplements, receipt-origin corrections and automatic financial-review requests. Historical imports and real customer price/quality policies still require their own validation.
- Document limits reserve enough receipt slots, event slots and accepted-quantity capacity to finish current custody tasks. A split or new arrival that would leave existing tasks unable to complete is rolled back; a full remaining putaway/scrap can use its reserved completion capacity. Direct receipts and staged acceptance share the same total quantity cap, and mixed excess/normal receipts use per-product completion rather than exact forecast equality.

### Quarantined supplier returns

- Apply migrations `warehouse_021_asn_supplier_return.sql` and `warehouse_022_asn_supplier_return_menu.sql` with writers stopped and a verified backup. The exact-JSON startup guard also checks the final event columns, so a partially applied migration cannot enable writes. The three new permissions are not automatically granted to existing roles.
- POST `/warehouse/inbound/{id}/custody/{action}` also accepts `approveReturn`, `cancelReturnApproval`, and `returnSupplier`, each with its own `warehouse:asns:{action}` permission, common request ID, revision and reason. Current scope and permission apply even before replay.
- `approveReturn` requires task, positive quantity, recipient (max 200), destination (max 1000) and approval reference (max 200). It reserves only unreserved held units, records immutable stock/inspection/recipient evidence, and moves no stock or money. An active approval prevents reinspection; putaway and scrap may consume only the unreserved portion.
- `returnSupplier` requires task, exact approval ID, quantity, handoverReference (max 200), and strict boolean `confirmHandover: true`. It deducts only the exact approved custody layer, records recipient/destination and the handover receipt, and increments handed/returned quantities atomically. Concurrent/repeated requests cannot duplicate the handover. Request fields cannot replace the approved recipient or address.
- `cancelReturnApproval` requires task and approval ID; it releases only the unhanded remainder. Earlier handovers are not reversed. Capacity accounting reserves events both to cancel each outstanding approval and to finish ordinary inspection/disposition, avoiding a document limit that would force physical handover.
- Detail projections add `supplierReturnApprovals` and task `returned` / `returnReserved`; scrapped quantity excludes returns. Approval, physical ledger, event, audit and request journal share the transaction. Supplier returns do not increase accepted quantities, generate unit/SKU goods-in fees, or invent refunds. Closure still requires all held units resolved and explicit shortfall confirmation. This workflow covers unaccepted quarantined arrivals; returns from normal accepted inventory, carrier pickup bookings and financial refund policies remain separate work.

### Linked late receipt supplements

- Apply migrations 023 / 024 before startup. POST `/warehouse/inbound/{original}/lateSupplement` requires the distinct `warehouse:asns:lateSupplement` permission, current original revision, request ID and a nonblank reason. This grants approval of the supplement and its charging policy; it does not grant normal ASN creation, receiving or finance access. No automatic role grants are made.
- The original must be a native CLOSED ASN and must not itself be a supplement. The child inherits its client, warehouse and currency. Supply reference, deliveryType, optional expectedDate/notes, 1–200 unique original-product lines, and explicit `adminPolicy: included|separate` plus `skuPolicy: group|separate`. Missing policies, unknown products, protected fields and nested supplements are rejected. Above the original unallocated shortfall, strict boolean `approveAdditional: true` is required; the immutable link records matched shortfall and additional approved quantity per product. At most 250 supplements per original, including cancelled records.
- Creation does not reopen, revise or move stock on the original. Original closure JSON, revision and charges remain unchanged. The supplement uses the normal direct/custody receiving and closure flows, with its own stock sources, fees, revisions and retry journal. Its approved forecast and policies cannot be edited; an unreceived child can be cancelled through the existing cancellation permission and replaced by a newly approved child.
- All supplement writers lock the original before the child and other business records. Shortfall matching reads current linked children under that lock. Open children reserve their matched forecast; cancelled children reserve zero; closed children retain only the matched quantity actually accepted. This prevents concurrent approvals from double allocating a shortfall and allows replacement of unaccepted quantities after short closure. Original shortfall itself is never rewritten.
- `group` prices SKU fees once across the original and all group-policy children, including concurrent direct receipt and custody putaway. `separate` bills a child independently. Under the same root lock, current billed-SKU evidence is merged before rate validation and assessment. The charge evidence records the group basis. Explicit `included` administration overrides only the quote client snapshot to zero and also retains the configured client snapshot; it never changes client master rates. Unit charges, actual delivery and labour remain chargeable under configured rates. This does not waive the entire supplement or backdate prices.
- ASN detail exposes safe `lateSupplement` / `lateChildren` links, approval policies and quantities; original detail also exposes `lateRemaining`. Prices and internal billed-SKU sets are excluded. Current scope/permission checks precede request replay. Creation, link, reference protection, audit and request completion are atomic. This flow covers known products on a new linked ASN; unknown-product identification, transferring already recorded unidentified physical arrivals, receipt correction and automatic financial review remain separate work.

## Order scanning and packing

- Apply `warehouse_009_order_work.sql` and `warehouse_010_order_work_menu.sql` after earlier migrations. They add scan evidence, package headers/lines and five separate function permissions. Existing employee roles receive no automatic grants.
- POST `/warehouse/orders/{id}/work` accepts `action`, `requestId` and `_version`. Actions `scan`, `unscan`, `pack`, `unpack` and `reopenpick` require their matching `warehouse:orders:*` permission and current client/warehouse scope, including on replay. An order lock serialises work; an already committed request returns its recorded response without applying again. Refresh details after resolving an older pending result before continuing against a newer version.
- `scan` takes `allocationId`, `barcode` and optional `serial`. One request records exactly one unit against a reserved allocation. Barcode/UPC must match exactly; SKU is allowed only when neither code is configured. Ambiguous client barcodes and mismatching reserved serials fail. Scanning requires ALLOCATED; PICKED orders can reopen picking after every package is voided.
- The client's `requireScan` is supported. Required scanning is frozen on the order and cannot be disabled by later changing the client flag. The first voluntary scan also makes scanning and packing mandatory. Such orders must scan every allocated unit before picking and seal every allocated unit before despatch. Ordinary orders that have never required or started scanning retain manual picking/despatch.
- `pack` requires PICKED and complete scanning. Supply a unique-per-order `packageCode`, exact positive `weightKg` (up to 100000, 3 decimals), `lengthCm`/`widthCm`/`heightCm` (up to 1000, 2 decimals), optional `notes` and `lines: [{allocationId, quantity}]`. Package quantities cannot exceed remaining allocations. Cancelled package codes remain reserved. Measurements do not automatically calculate carrier postage or packaging-material consumption.
- `unscan` takes `scanId` and `reason`; it cannot reduce scanned quantity below packed quantity and returns the order to ALLOCATED. `unpack` takes `packageId` and `reason` and voids an undispatched package. `reopenpick` requires a reason. None changes on-hand stock. Cancellation voids active work records and releases reservations. Despatch freezes package count/weight, marks packages DESPATCHED and commits inventory, billing and audit together. Dispatched orders cannot undo work.
- Limits: 20000 scan events and 200 package records per order (including void history), 1–200 distinct allocation lines per package. Detail responses expose complete allocation totals, all package manifests and the latest 100 scans. This is a keyboard-input scanner workflow, not validated physical scanner/printer integration or a wave/packing-station system. Bulk orders beyond these limits require a separate workflow.
- Vue uses the existing per-actor order pending-request journal for all five actions. A lost response blocks further writes; reload/retry retains the original nonce, version and body. Operational records expose no pricing snapshot. Tests use synthetic local data only.

## Stocktakes

- Apply `warehouse_011_stocktake.sql` and `warehouse_012_stocktake_menu.sql` before deploying this version: all inventory writers now consult `wh_stocktake_lock`. POST `/warehouse/stocktakes` requires `warehouse:stocktakes:add` and selects one client, one warehouse and 1–100 locations. The transaction freezes this client's location scope and snapshots up to 2000 existing stock pools. Empty locations are also frozen so new pools cannot slip into the count.
- GET `/list` and `/{id}` require separate list/query permissions and client/warehouse scope. POST `/{id}/actions` supports `count`, `found`, `submit`, `reopen`, `approve`, `cancel`, each with its matching permission, original `requestId` and `_version`. Scope is checked before replay; unknown responses must be retried with the same request, including after browser reload.
- `JAVA_STOCKTAKE_V1`: COUNTING → REVIEW → APPROVED; an open count may be CANCELLED. `count` saves 1–200 `{id, counted, reason}` rows; missing numbers are not zero. Every discrepancy requires a reason. `found` adds a tracked physical product in a selected location; it does not immediately create stock. `submit` requires every line counted, including explicit zeros. `reopen` requires a reason, clears entered counts and retains prior evidence in audit; the freeze remains.
- Approval requires an actor who neither created nor participated in the count. A real superadministrator can explicitly provide `selfApproval: true` and an approval reason for an audited exception; ordinary actors cannot. APPROVED records store per-line adjustments, approver and reasons. Reopening an approved count is not supported; start another count to correct later discoveries.
- Every stock writer acquires location parents before checking freezes. Manual movements, ASN receipts, existing-order work and reservation release/consumption reject frozen stock. Order allocation skips frozen locations and may use eligible stock elsewhere. Inventory listing exposes `stocktakeId` and `unreserved`; frozen pools report `available: 0` without changing on-hand or reservations. The location's warehouse/client/type/custody identity cannot change while it has an active freeze. Cancellation can still release the original freeze after client policies change.
- Approval validates original pool revisions, on-hand quantities and reservations, then posts shortages before surpluses. Reserved units cannot be lost through a count. Shortages consume only unreserved source layers; surpluses create a new current-time source layer, without inventing an old receipt date. Capacity, tracking and serial uniqueness are checked. Stock, layers, ledger, line results, audit, document status, nonce and unfreeze commit together; any failure retains the freeze and previous stock.
- Counting does not trigger receiving or order fees. Custody/quarantine and blind-count modes are not implemented. A reserved-stock shortage requires cancellation of the count, resolving the affected orders, then a fresh count. Warehouse personnel must observe the physical freeze; software cannot prevent unrecorded physical movements.

## Customer returns

- Apply `warehouse_013_returns.sql` and `warehouse_014_returns_menu.sql` before this service version. `/warehouse/returns/list` and `/{id}` require their own list/query permissions; POST creates an RMA from `{requestId, order, product, quantity, reference, reason}` with `warehouse:returns:add`. One RMA covers one physical product from one native despatched order in its original warehouse. The consumed allocation evidence must account for the full original order product quantity. Open RMAs claim their expected quantity; cancelled claims are released; closed short RMAs retain only the actually received quantity. Concurrent claims serialize on the source order.
- Actions use POST `/{id}/actions` with `requestId`, `_version`, `action` and action-specific permission. `receive` accepts an original `allocation`, quarantine custody `location` and positive integer `quantity`. Cumulative receipt quantity across all RMAs must not exceed the original consumed allocation. Client-supplied batch, serial, source age, price or status fields are rejected. At most 250 receipts per RMA; each operation is at most 10,000,000 units.
- Physical receipts create stock in an active `Quarantine` location with `custodyOnly: true`, preserving original source origin, receipt age, batch, serial and expiry. Such stock is on hand but exposes `quarantined: true` and `available: 0`; allocation, manual removal/transfer and ordinary stocktake cannot consume it. A location holding stock cannot change client or custody/quarantine classification to bypass inspection. Capacity and cross-location serial uniqueness still apply.
- `inspect` takes `receipt`, `result: PASS | FAIL`, and `reason`. Reinspection is allowed before any disposition; earlier decisions remain in the audit. After partial disposition the original inspection is immutable. `restock` takes receipt, quantity, normal destination location and reason; it requires PASS. `scrap` takes receipt, quantity and reason; it requires FAIL. Distinct action permissions apply. Inspection alone does not release stock. Restocking moves exact held source layers, retaining their original origin and age; scraps reduce held stock without inventing saleable inventory. Targets honor freezes, capacity, active physical products, client stop policy, warehouse restrictions and tracking requirements.
- Expiry policy follows product override, otherwise client configuration, otherwise Warn. BlockExpired rejects expired restocking; Warn permits an inspected release with `expiredAtDisposition: true` in the immutable disposition evidence and a warning on the page. Receipt into custody and scrap remain possible under either policy. Required missing tracking is not fabricated.
- `close` requires receipt and disposition totals to match with no held remainder, plus a reason. If fewer than expected arrived, the superadministrator must explicitly submit `approveShortfall: true`; this releases the unreceived claim for a future RMA. `cancel` requires zero received quantity and a reason. Both retain all audit records. Status progression is NEW → PARTIALLY_RECEIVED / RECEIVED → CLOSED, or an unreceived NEW → CANCELLED.
- Return handling rates are snapshotted at creation: explicit product first/additional overrides client rates, including an explicit zero. Missing/invalid rates do not silently become free. Each RMA receives one first-item fee and subsequent units use the additional-item fee, independent of partial receipts. Monetary posting uses the difference between rounded cumulative totals, preventing split-receipt rounding drift. Each receipt creates an UNCONFIRMED Returns charge with immutable source evidence; these charges enter the existing invoice workflow. Scrap does not automatically refund handling fees. RMA rates are redacted from normal/generic reads and replay responses unless the current actor has finance query permission.
- Head version, receipt/inspection/disposition, physical stock, layers, ledger, fee, source evidence, audit and request journal commit atomically. A lost response must be retried using the exact request ID and content; browser reload retains that request. Current permissions and client/warehouse scope apply before a replay. Legacy unlinked returns, mixed source investigations, multi-product parcel grouping, cross-warehouse returns, platform refunds and credit-note policies are not covered by this workflow and remain replacement work.

## Runtime configuration

The default `prod` profile has no database password, Redis password or signing-secret defaults. Required variables: `WAREHOUSE_DB_URL`, `WAREHOUSE_DB_USERNAME`, `WAREHOUSE_DB_PASSWORD`, `WAREHOUSE_REDIS_HOST`, `WAREHOUSE_REDIS_PASSWORD`, `WAREHOUSE_TOKEN_SECRET`. Supply an independently generated JWT secret with at least 32 random bytes. The unchanged upstream token implementation derives the HS512 signing key using SHA-512; it does not itself enforce secret entropy. Optional non-secret connection variables include `WAREHOUSE_REDIS_PORT` (6379), `WAREHOUSE_REDIS_DATABASE` (0), `WAREHOUSE_HTTP_PORT` (18080) and `WAREHOUSE_BIND_ADDRESS` (127.0.0.1). The Druid monitoring servlet remains disabled.

Explicit `SPRING_PROFILES_ACTIVE=local` selects isolated defaults: HTTP 127.0.0.1:18080, MySQL 127.0.0.1:13306/warehouse_local and Redis 127.0.0.1:16379. It still requires `LOCAL_DB_USERNAME`, `LOCAL_DB_PASSWORD` and `LOCAL_TOKEN_SECRET`; no credentials are committed. `LOCAL_DB_URL`, `LOCAL_REDIS_HOST`, `LOCAL_REDIS_PORT`, `LOCAL_REDIS_DATABASE`, `LOCAL_REDIS_PASSWORD`, `LOCAL_HTTP_PORT` and `LOCAL_UPLOAD_PATH` can be supplied by private local tooling. Local Redis alone permits an empty password for the isolated loopback instance. No database is auto-created or initialized by these configuration files.

Set `WAREHOUSE_LOG_PATH` to a private local directory when testing. Keep generated uploads, logs, SQL exports, process environment and local bootstrap credentials outside tracked source. Local source cleanup does not change the existing production deployment or its database; production cutover remains separate from this migration.

All business periods and timestamps use UTC. The master pool initializes each database session with `SET time_zone = '+00:00'`; supply `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true` in the JDBC URL as well. A read-only startup check compares database session time, UTC time and Java time, and refuses business startup if they disagree. This changes only application sessions, not the MySQL host's global timezone. Early local synthetic fixtures created before this guard are not evidence for historical timestamp accuracy; final timestamp verification uses new fixtures and checks database epochs against API instants.


## Historical storage billing

- Apply `warehouse_015_storage_history.sql` before upgrading: native master and physical-stock writers now consult its control table, even while recording is disabled. No migration enables recording or posts charges automatically.
- GET `/warehouse/finance/storage-history/status` and `/day?client=...&date=YYYY-MM-DD` require financial query permission. POST `/start` requires finance edit plus the real superadministrator, `{requestId, confirm:true}`. It snapshots existing master records, physical pools and source layers under locks, at the current database time. Repeated activation is harmless. There is no API to backdate, stop recording, inject historical snapshots or overwrite evidence.
- Each successful native transaction records one final-state batch for changed physical pools or relevant master records. Manual movements, ASN receipts, despatch, stocktake adjustments and return dispositions share this capture path. Reservations alone do not change physical history. History, stock, financial effects, audit and the business transaction roll back together. Source quantities must reconcile. A short control-row lock serializes batch sequence and database time; clock regression rejects the operation. Historical payload hashes are checked on read.
- `/billing/preview` and `/billing/commit` accept `mode: Storage` for at most 366 completed UTC days, using only history after the first complete recorded day. Daily, Monday–Sunday weekly and calendar-month periods must be whole. Seven calculator modes are supported: unit, volume, carton volume, pallet unit, occupied location type, peak occupied location type and fixed stock-management fee. Missing required prices or history is an error, not zero or substituted current stock.
- Pricing policy `PERIOD_END_V1` uses closing physical quantities, dimensions and historical rates. Peak mode uses the maximum occupied-location count per type across committed states in the period, including its opening state, priced at the period end. The history includes stock in return quarantine. This is an explicit implemented policy, not a claim that every customer contract uses it. Frequency, billing-mode or currency transitions inside a multi-day period require review; runs cannot add amounts in different currencies.
- Client-specific active location prices take precedence over shared active prices for the exact location type and frequency. Only administrators can maintain shared prices. Reassignment or deletion of a rate removes it from the old client's later history; it does not rewrite earlier periods.
- The entire historical warehouse scope is required, including warehouses occupied earlier in the period. Quotes and immutable source evidence retain historical inputs and pricing policy. Posting claims every client/day with a unique constraint and records warehouse references on fees, runs and invoices; overlapping dates cannot be charged again through another frequency. Response-loss recovery reuses the original request and quote hash.
- Invoices use the recorded charge currency and reject mixed currencies, even after the client changes its current currency. Existing invoice-time tax policy still applies; this is not historical tax-policy reconstruction.
- Automatic storage settlement, legacy history import, free-storage/promotional periods, contract-specific prorating, historical tax rules and customer invoice reconciliation remain outside this checkpoint. Database writes outside these native services bypass the recorder and are not supported. Production cutover still requires exclusive native write ownership, import reconciliation, backup and capacity testing.

## Financial adjustments and credit notes

- Apply `warehouse_016_finance_adjustments.sql` and `warehouse_017_finance_adjustment_menu.sql` before upgrading. Existing invoice operations now consult approval reservations even when no adjustment exists. New permissions are not granted to roles automatically.
- Financial query permission protects GET `/warehouse/finance/adjustments`, `/adjustments/source/{chargeId}`, `/adjustments/{id}`, `/credit-notes`, `/credit-notes/{id}` and POST `/adjustments/{id}/preview`. Lists accept `pageNum`, `pageSize`, `client`. Requests and credit notes require the entire charge and invoice warehouse scope, including invoices created after the request. Generic record endpoints cannot expose these aggregates.
- POST `/adjustments` requires finance edit and `{requestId, chargeId, reason, evidenceRef}`. It freezes the recorded original fee identity; it does not change an ASN, order, stock or invoice. A request starts in `REVIEW`.
- Preview accepts `{_version, decisions:[{component, quantity, decision:"reduce"|"retain"}], reason, issueDate?, taxPointDate?, accountingPeriod?, reconsiderationOf?, reconsiderationReason?}` and returns `{plan, quoteHash}`. Only verified original raw component quantities/rates are used; when exact quantity evidence is unavailable, the explicit basis is `NET_AMOUNT`, with two decimal places. ASN unit counts are integral; labour hours allow three decimals. Original raw remainders and Half-Even rounding determine net and original invoice tax deltas. Today's client currency, VAT or prices do not rewrite old invoice credit evidence. Negative source fees/components are not eligible for this reduction workflow.
- POST `/adjustments/{id}/actions` requires `{requestId, _version, action}`. `approve` and `revoke` require `warehouse:finance:approveAdjustment`; `execute` requires `warehouse:finance:executeAdjustment`; `cancel` requires finance edit. Approval additionally takes the exact `planInput` and `quoteHash`; revocation/cancellation require a reason. Approval reserves the fee and freezes all invoice mutations until execution/revocation. Execution rechecks original evidence, effect sequence, invoice, policy revision, current scope and permission. Permission is checked on retries too. Decisions are immutable; reconsidering a prior retain decision requires its effect reference and a new explanation.
- Execution preserves original charge `amount` and evidence. Unbilled reductions change `billableAmount` for future invoicing; draft reductions create a replacement draft, retain the previous `SUPERSEDED` invoice and snapshots, and move all fee claims together. Confirmed invoice reductions create a separately numbered immutable credit note, preserving original invoice contents. `adjustedAmount` is the remaining fee net amount, not a payment or settlement ledger. An invoice with posted credits cannot be unconfirmed. Zero-value outcomes do not create a cash credit.
- GET/POST `/adjustment-policy` is restricted to the real superadministrator; save additionally requires finance edit. Payload: `{requestId, _version, policy:{version, taxMethod:"original-line-remainder-half-even", requireDifferentActor:boolean, creditPrefix, seller:{name,address,taxId}, buyers:{clientId:{name,address,taxId}}}}`. Prefixes use uppercase letters, digits and hyphens. A changed policy needs a new version name; policy changes invalidate pending plans. The singleton policy is locked while previewing/approving/executing so policy edits cannot race execution. No seller/buyer identity is installed by SQL. Separate approval/execution actors are required by default and unless policy explicitly disables separation.
- Nonzero confirmed credits require configured seller and buyer, issue date and tax point date no later than today UTC, and explicit `YYYY-MM` accounting period. These are recorded document values, not an assertion of jurisdiction-specific accounting compliance. Vue prints the immutable credit with escaped content and no external resources; no cash refund, payment reconciliation, Xero sync or email is performed.
- Approval history, effect sequence, credit numbers, original invoice links, actor evidence, audit and request journal commit together. Concurrent execution or retry of the same request returns one effect/note; posting failure rolls back the amount, number, reservation consumption and journal. Policy and approval evidence are checksum-verified.

## Exact decimal document storage

Unidentified-arrival evidence added by migration 025 follows the same exact LONGTEXT rules; see the additional workflow below.

- Apply `warehouse_018_exact_json.sql` with native writers stopped and a verified backup. It converts 16 document columns in 13 warehouse tables to UTF-8 LONGTEXT with enforced `JSON_VALID` checks. Native relational DECIMAL columns and all upstream RuoYi tables remain unchanged. MySQL 8.0.16+ is required; startup fails if expected exact columns or enforced constraints are absent, or if warehouse binary JSON columns remain.
- A real MySQL round-trip exposed lost fractional digits when the text JSON value `1000000000000000000000.25` was stored in a native JSON column. Fractional numeric text can be represented as DOUBLE by native binary JSON; see [MySQL's verified numeric conversion example](https://bugs.mysql.com/bug.php?id=92331). Merely deserializing that rounded value as BigDecimal cannot recover lost digits. The new text storage preserves Java's original decimal spelling and checksums. Do not use MySQL JSON numeric extraction for financial arithmetic; read full documents through `WarehouseJson` and calculate with BigDecimal.
- HTTP map bodies use `USE_BIG_DECIMAL_FOR_FLOATS` as well as the stored-document parser. API clients should send decimal strings; decimal JSON numbers are also parsed without an intermediate Double. Financial responses preserve exact decimal strings. Quotes and hashes do not depend on MySQL reserializing a number.
- The migration preserves previously stored values; it cannot reconstruct previously lost digits. Reconcile imported or older records against source evidence, and keep mismatching records blocked. Do not guess or silently rewrite amounts, historical snapshots or approval hashes. The isolated local precision failure fixture is retained as evidence.
- Local evidence covers preserved pre/post-migration content hashes, all enforced checks, old-schema startup refusal, a numeric HTTP request at DECIMAL(24,2) precision and two successive cent reductions, historical fee source reads, native ASN/order/return regressions, and real Vue approval/execution/printing after conversion. Production conversion and restoration rehearsal remain required before cutover.

## Unidentified physical arrivals

- Apply migrations 025 and 026 with native writers stopped and a verified backup. Startup requires the new columns and enforced quantity/decision/JSON checks. No existing role receives the four new permissions automatically.
- POST `/warehouse/inbound/{id}/unknown/{action}` requires `warehouse:asns:{action}`. Actions are `unknownArrive`, `unknownApprove`, `unknownExecute`, `unknownCancel`. All require `requestId`, `_version`, and a nonempty `reason`; input keys are strict. Current client/warehouse scope and permission are checked before replay. Only open native ASNs accept these actions.
- `unknownArrive` takes `location`, integral `quantity`, `description`, `evidenceReference`, optional `barcode`, `batch`, `serial`, `expiry`. The location must be dedicated quarantine. Observed serials have quantity one. The physical record and aggregate occupancy reserve actual capacity together with known stock, without inventing a SKU or acceptance fee. Arrivals block forecast edits, cancellation, direct receiving and closure until resolved. Location/client/warehouse history and ownership protections include anonymous custody.
- `unknownApprove` takes `arrival`, `decision`, `quantity`, `reference`. `identify` additionally requires `product` and verified tracking. It retains nonempty originally observed tracking and snapshots product revision; missing mandatory product tracking must be supplied. `returnSupplier` and `scrap` instead require `recipient` and `destination`, with no product/tracking fields. Approval reserves unused quantities only and performs no stock movement.
- `unknownExecute` binds `arrival` and `approval`, with integral `quantity`. Identification rechecks the approved product revision and tracking, reduces anonymous occupancy, and creates a normal pending inspection task. Its inventory source points to the original arrival and retains the original UTC arrival time. Previously unforecast products appear as server-owned exception lines with zero expected quantity; stored original forecast lines are unchanged, and excess approval remains necessary before acceptance. Physical return/disposal instead requires `confirmPhysical:true` and the actual `reference`; it removes only the approved anonymous quantity, retaining recipient/destination evidence. No courier booking, payment refund or fictitious SKU ledger is generated.
- `unknownCancel` takes only `arrival` and `approval` beyond common fields and releases all unused approval quantity. Executed quantities and evidence cannot be withdrawn. Each ASN is limited to 250 anonymous arrival cases and shares physical-unit/receipt completion limits with known custody. An independent 2,000-event budget reserves enough space for cancellation and final resolution.
- Detail projections include `unidentifiedArrivals`, `identificationApprovals` and `unidentifiedEvents`. Counter changes, known source creation, original arrival quantity disposition, request replay, audit and storage capture commit or roll back together. Identification records the anonymous reduction and known inventory in one history batch, so location usage is not double-counted. Anonymous stock contributes to location-based and peak storage fees. Product-dependent pricing refuses historical periods ending with unidentified goods; it never silently prices them at zero. Historical billing review is described below; original physical history remains immutable. This checkpoint does not provide unknown-goods transfer from closed ASNs, appointments or original receipt corrections.


## Historical storage identity review

- Apply migrations 027 and 028 with writers stopped and a verified backup. Review documents/events retain exact decimal JSON and checksums. Startup requires their enforced JSON, status and revision constraints. The new `warehouse:finance:approveStorageReview` permission is not granted automatically.
- Financial query permission protects GET `/warehouse/finance/storage-reviews/context?client=...&from=...&to=...`, `/products?client=...&q=...` and `/{id}`. Context requires one exact completed, unbilled UTC storage period; a consumed review remains readable through its frozen original period. Product search returns only identity fields for the scoped client, without needing master-data write permission. Every historical warehouse must be in the current user's scope.
- POST `/storage-reviews/preview` accepts `{client,from,to,planInput}`. `planInput` is `{allocations:[{arrival,product,quantity}],productFacts:[{product,...}],reason,evidenceReference}`. Allocate every period-end anonymous quantity exactly once in total, with positive integral quantities and no duplicate arrival/product pair. Up to 2,000 allocations are accepted. Products must belong to the same client. Existing historical facts cannot be overridden. A product absent from period-end history requires explicit evidenced facts for the historical mode: StorageUnits uses unitStoragePrice; Volumetric uses volume; VolumetricCarton uses unitsPerCarton/cartonHeight/cartonLength/cartonDepth; PerPalletUnit uses unitsPerPallet/unitStoragePrice. Capacities and dimensions must be positive. Zero product rate retains the historical client fallback rate, never today's rate. Known and reviewed quantities of the same SKU are combined before carton/pallet rounding.
- POST `/storage-reviews` requires finance edit, the preview input plus `requestId`, `quoteHash`, and `_version` when updating an existing draft/revoked review. One review exists per client and exact period. Revisions preserve immutable full evidence, original history hash, product revisions, reviewed context and quote. The original physical stock, anonymous arrival, forecast and history are not changed.
- POST `/storage-reviews/{id}/actions` takes `{requestId,_version,action:"approve"|"revoke",reason}` and requires the dedicated approval permission. A preparer cannot approve their own draft. Approval rechecks all history and product identities. Revoke applies only to unused approvals; product revision or revocation invalidates pending billing previews. Scope and permissions are rechecked on replay.
- Ordinary storage period billing consumes the approved review. The approver cannot post that charge. The fee, source evidence, client/day claims, review CONSUMED revision, audit and original request journal commit together; retries cannot create a second effect. Consumed approval cannot be revoked. Subsequent reductions use financial adjustments; this process does not automatically issue an invoice, credit, refund or stock movement.
- This is an evidenced financial interpretation, not a historical stock rewrite or proof of customer tariff parity. Original anonymous history remains visible. Production historical imports, automatic reviews/settlement and client invoice reconciliation still require separate implementation and acceptance. The supported receipt correction scope follows below.

## Excess receipt recording corrections and financial review

- Apply migrations 029 and 030 with writers stopped and a verified backup. Three correction permissions (`warehouse:asns:approveCorrection`, `executeCorrection`, `cancelCorrection`) are separate and are not granted automatically. Startup validates exact JSON columns, review scope columns and enforced state/quantity constraints.
- GET `/warehouse/inbound/{asn}/corrections/context?receiptLine=...` requires ASN query permission and traces the immutable original receipt line through audited native manual-transfer pairs. Shared lot/origin IDs alone never establish a relationship: separate putaways from one custody origin remain separate receipt sources. All traced warehouses must be in scope; missing or unverifiable transfer evidence stops the operation. Returned shipment descendants are not included. Native direct receipts and accepted quarantine putaways are supported.
- POST `/warehouse/inbound/{asn}/corrections/preview` requires approval permission and `{_version,receiptLine,allocations:[{layer,quantity}],reason,evidenceReference}`. Quantities are positive whole numbers, unreserved and still on hand, bounded by the original uncorrected receipt quantity; stocktake freezes are respected. A maximum of 200 selected sources, 2,000 traced nodes and 500 corrections per ASN bounds review size. Duplicate, foreign, quarantine-only or insufficient layers are rejected.
- POST `/warehouse/inbound/{asn}/corrections` adds `requestId` and the server `quoteHash`. Approval preserves the original ASN version, receipt, complete source graph, product/pool revisions and selected quantities. It does not reserve stock. GET `/{correction}` returns the full approved evidence; ordinary ASN details return compact correction history. Original records remain immutable.
- POST `/{correction}/execute` and `/cancel` use `{requestId,_version,reason}` where `_version` is the correction revision. Execution additionally requires `confirmRecordedError:true` and a person other than the approver. A changed ASN, reservation, product or source graph invalidates execution; cancel the unused approval and preview again. Cancellation never moves stock. Current permissions and all recorded warehouse scopes are checked before request replay.
- Execution atomically reduces the approved source layers and pool quantities, appends inventory/storage history, changes effective ASN `received` counts, marks the correction executed and creates exactly one financial review case. It never rewrites original receipt rows, source age or fees. Open ASN status reflects effective counts; CLOSED ASNs stay closed with their original `closedAt` and stored `shortfall`. Later supplement approval records original closure shortfall, effective shortfall after corrections, and shortfall still unallocated to other supplements as distinct evidence. An entirely corrected open ASN can receive again or use explicit administrator shortfall closure; original receipts still prevent editing/deleting the forecast.
- GET `/warehouse/finance/review-cases` supports `pageNum`, `pageSize`, `client` and `status` (`OPEN`, `LINKED`, `RETAINED`, or empty). Finance query permission and current client, all source warehouses and invoice aggregate scope apply. GET `/{case}` includes immutable original charge components and current remaining monetary quantities. Multiple corrections to one receipt have separate cases while adjustments share the original charge's existing reduction limits.
- POST `/warehouse/finance/review-cases/{case}/actions` requires finance edit and `{requestId,_version,action:"adjust"|"retain",reason}`. `adjust` creates one linked ordinary financial adjustment request in the same transaction; it still requires component decisions, monetary preview, approval and separate execution under the existing financial workflow. `retain` records a mandatory explanation without changing money. Replay cannot create duplicate adjustment requests; audit failure rolls back the case, adjustment and journal together.
- This scope corrects quantities mistakenly recorded in excess. It is not physical disposal, supplier shipment, customer refund, SKU/batch relabelling or recovery of goods already shipped. Other ASN exception types do not yet enqueue financial review automatically. Production tariff parity and cutover remain subject to the replacement acceptance checklist.

## Master data file transfer

- Apply migrations 031 and 032 with writers stopped and a verified backup. `wh_master_import` retains exact JSON, a checksum and state/version constraints. Each of clients, products, warehouses, locationTypes and locations receives separate import/export permissions; no role is granted these automatically. Existing add/edit/query permissions, administrator-only creation, current client/warehouse scope and financial-field access remain mandatory.
- POST multipart `/warehouse/master/{kind}/imports/preview` takes `mode=create|update` and `file`. Only UTF-8 CSV and ordinary XLSX are accepted: 2 MiB compressed/input, 32 MiB expanded XLSX, 150 columns and 500 data rows maximum. The first worksheet is the data sheet; a second generated instruction sheet is informational. Formula/error cells, numeric identifiers/dates, macros, embedded objects and external workbook links are refused. CSV quoted commas, embedded newlines and BOM are supported. XLSX handling uses the existing Apache POI dependency and [value/worksheet APIs](https://poi.apache.org/components/spreadsheet/quick-guide.html); no formulas are evaluated.
- Headers accept actual field keys or exact available Chinese/English labels. Unknown, duplicate and protected headers are rejected. Empty cells omit a field, retaining defaults on create or current values on update. `__CLEAR__` explicitly clears an optional field; prefix a backslash to keep a literal marker (export escapes it reversibly). References accept an existing ID or exactly one visible display name; ambiguity requires an ID. Create rows cannot contain id/version. Updates require a unique id per row and `_version`; they do not silently upsert.
- Preview executes the same master-data validation, reference checks, unique constraints, barcode checks and business writes under savepoints in a transaction that always rolls back. A row failure is reported by its file row; no partial master records, create/update audits or storage history are committed. Failed previews are not saved. A fully valid preview stores resolved inputs, original and resulting values, reference revisions and a canonical result hash in a separate transaction. At most 100 uncommitted previews per actor are retained; cancel unused previews before exceeding this capacity.
- GET `/imports` returns the current actor's latest 100 batch summaries; GET `/imports/{id}` returns permitted field differences only after current scope checks. Other actors, including administrators, cannot read this actor's stored batch through the API. Summary filenames/counts remain visible to their owner so stale previews can be discarded without exposing old business values.
- POST `/imports/{id}/actions` takes `{requestId,_version,action:"commit"|"cancel"}`. Commit rechecks import/add-or-edit/query and financial-field permissions, all business scopes, original versions and referenced records. It reruns the complete batch and compares the approved preview hash before commit. Any validation, version, reference, audit, or storage-history failure rolls back all rows, state changes and request evidence. Successful imports append ordinary per-record audit and one atomic storage-history batch when history is enabled. Replay reads the current committed batch with a lock, avoiding an old MySQL repeatable-read snapshot; it never applies rows twice. Cancellation changes only the owned preview and returns a summary, including when old references are gone.
- GET `/workbook?template=true&mode=create|update` downloads the currently writable schema and instructions. GET `/workbook?template=false&page=1&size=500&keyword=...` requires export/list/query and downloads the chosen 1–500-row slice with filtered total/page metadata, IDs and versions. All exported cells are strings, preserving leading zeros and decimal text while treating formula-looking text literally. Financial and administrator-only columns are omitted without the relevant access. An export containing readable financial columns may require removing those columns before an import by a user without financial edit permission.
- These endpoints transfer master records only. Production field mapping, historical stock/source migration, open orders and unsettled balances require their own implementation and acceptance; successful synthetic file imports do not establish a production migration.

## Shared suppliers and sales channels

- Migration 033 adds suppliers/channels menus with separate list/query/add/edit/remove/import/export permissions, without granting existing roles. Both kinds use the same master CRUD, CSV/XLSX preview/commit and filtered workbook endpoints described above, bringing supported transfer kinds to seven. Only the built-in super administrator (user ID 1) may create, update, delete or import these global catalogs; function grants alone do not permit shared writes. Authorized catalog reads/exports do not grant access to any linked client's or warehouse's business documents.
- Both require an explicit boolean `active` state (default true on create). Channel names are at most 100 characters, and case-insensitive `Manual` is reserved. Channel rename/delete is blocked by references or existing order/rule/charge channel names. Referenced suppliers cannot be deleted; supplier name/contact edits do not rewrite existing document snapshots. Deactivation is available for either kind.
- ASN create/update accepts optional `supplierId`; manual-order create/update accepts optional `channelId`. IDs are strings up to 64 characters. On update, omission keeps the existing identity and name snapshot, while an explicit empty string removes the association. A new or changed selection requires read access to an active catalog record. Keeping an existing selection does not re-require catalog access or active status; business-document permissions and scopes still apply. Supplier contact details are not copied onto ASNs. Late supplements inherit the original supplier identity/name, including after deactivation.
- Manual orders retain `source=MANUAL`, `workflow=JAVA_MANUAL_V1`, and manual shipping. The server derives `channel` from the selected record or the built-in `Manual` default; callers cannot override protected workflow/source/channel fields. Order charging and order-count tier registration use the stored channel name. Disabling a channel does not strand an existing order's allocation, picking or dispatch. This classification performs no marketplace authorization, order download, stock sync or carrier operation.
- A new non-Manual channel-tier rule must match the exact name of a registered active channel and stores a protected reference. An existing rule may retain its current inactive channel, or its pre-existing legacy text-only channel name, without requiring extra catalog-read permission. Changing that selection requires normal new-binding checks. Existing channel rename/delete protection also covers legacy name-based usage.
- Concurrent retries of successful ASN/order creation verify scope using a current locking read after the request journal lock. This avoids false not-found results from an earlier MySQL repeatable-read snapshot without repeating creation or dropping scope checks.
- Product multi-supplier relationships, purchase/drop-ship workflows, production tariff comparison and historical migration remain outside this implemented scope.

## WooCommerce connection and order intake

- Apply migrations 034 / 035 after stopping writers and verifying a backup. Four dedicated tables persist connections, pull jobs, inbox documents and source revisions; LONGTEXT/JSON validity and state checks are required by startup validation. The menu has separate `warehouse:integrations:list|query|configure|pull` permissions, without automatic role grants. Generic record mutation cannot write these tables.
- All paths below are relative to `/warehouse/integrations`. GET `/capabilities` reports provider, encryption-key availability, local-test mode and `intakeOnly=false`, `warehouseImport=true`, `remoteWrites=false`. GET `/` lists at most 200 scoped connections; GET `/{id}` reads one. POST `/` creates and PUT `/{id}` updates configuration. Only user ID 1 may configure, including when another user holds the configure permission. Reads and pulls require current client and warehouse grants.
- Configuration takes `requestId`, `name`, `siteUrl`, `client`, `warehouse`, `channel`, boolean `enabled`, optional `credentials:{consumerKey,consumerSecret}` and `_version` on update. Source URL and routing identities are immutable. A canonical site has one connection; URL aliases and aggregators still require actual merchant/source ownership validation. An absent credentials object preserves existing ciphertext; an explicit credentials object must contain both valid values. No secret or ciphertext is returned in public responses or audit. The latest save request ID is returned only to its owner for response-loss reconciliation.
- Credentials use AES-256-GCM with connection identity as authenticated additional data. The encryption key and exact allowed hosts are server environment configuration; see [INTEGRATIONS.md](INTEGRATIONS.md). Do not put credentials into a frontend environment, URL, browser recovery store or RuoYi repeat-submit cache. A missing encryption key does not prevent ordinary warehouse startup or saving a disabled draft without credentials. Enabling requires valid credentials, allowed host and active routing records.
- POST `/{id}/pull` takes `requestId`, `_version`, optional ISO UTC `since` and optional boolean `restartWindow`. The first pull requires `since`; continuation uses the persisted window without changing its start. Each synchronous call reads at most ten orders. While holding a connection-specific MySQL session lock, a job first commits its original input and fixed UTC window, then reads the provider, and finally commits inbox documents, revisions, cursor, success and audit in one transaction. A completed actor/request replay does not make another HTTP request. A running job whose session lock disappeared can resume using the same actor and original input. A live competing request fails; it must not replace the pending request ID.
- GET `/{id}/jobs?pageNum=1&pageSize=20` returns `data:{rows,total}`, with states `RUNNING|SUCCEEDED|FAILED`, fixed error codes, result counts and UTC timestamps. Original request input and request ID are only returned to the original operator. `recoverable` additionally requires a RUNNING job with no live connection lock. Saving configuration under the same lock can end an abandoned job as `CONNECTION_CHANGED`; ordinary employees cannot do this.
- GET `/{id}/inbox?pageNum=1&pageSize=20&state=...` returns `data:{rows,total}`. States are `AWAITING_REVIEW|HELD|CANCELLED|FULFILLED`. GET `/{id}/inbox/{item}` returns the current normalized document and up to 100 revision summaries. External identifiers, SKU text and money retain exact source representation. Unchanged documents do not add a revision; older source modification timestamps cannot overwrite the latest snapshot. Changed pagination totals fail the page without cursor progress and require an explicit window restart. Completed windows overlap the next read by two minutes.
- Current account status, role permission and routing scope are checked before network access and again before final commit. Page-validation failure, revoked access or database failure commits no partial inbox update or cursor advance. Failure details use fixed codes, never provider response bodies. If the failure-record transaction itself cannot complete, the persisted job remains recoverable rather than falsely reporting a completed pull.
- Transport uses HTTPS, exact host allowlisting, validated DNS results at connection time, normal TLS verification and no proxy, redirect, automatic retry, cookie storage or response compression. Total deadline is 45 seconds, individual network phases at most eight seconds and response body at most 2 MiB. The local HTTP exception requires an explicit test profile, loopback server bind and one exact loopback origin; remove it after synthetic protocol tests.
- Every initial inbox document is `verification=ORDER_DETAILS_ONLY`. Its AWAITING_REVIEW state alone does not authorize warehouse work. The dedicated acceptance flow below performs the additional source/product checks and creates a linked warehouse order. No inventory update, carrier purchase, fulfillment write, refund, webhook or scheduled pull is implemented by this adapter. Other platforms/carriers and real store authorization remain separate acceptance work.

### Source ownership, SKU mapping and warehouse acceptance

- Migrations 036 / 037 add `wh_integration_authority`, `wh_integration_mapping`, `wh_integration_order` and independent `authority|mapping|review|accept` permissions. No existing role is granted these permissions automatically. Startup requires the new evidence JSON and enforced state constraints. Inbox list responses add `warehouse_order_id`; details add `warehouseOrderId` and normalize revision timestamps to UTC.
- GET `/{id}/acceptance-settings?item=<inboxId>` requires query permission and scope. It returns the source policy and up to 200 mappings, restricted to the specified inbox's source product/variation pairs when supplied. This avoids losing an older mapping among unrelated recent mappings. `acceptedLines` retains the immutable accepted SKU/eligibility snapshot after reload, independently of later mapping changes.
- PUT `/{id}/authority` is additionally super-admin only. It accepts `requestId`, `_version` (zero on create), `sourceIdentity` (canonical store URL), ISO UTC `cutoverAt`, `fulfillmentMode:CORE|LEGACY_METADATA`, boolean `active`, `reason` and `exclusiveSource:true` when enabled. Identity and cutover are immutable. The source identity hash is unique across accepting connections; it depends on the administrator's actual source reconciliation and is not an automatically discovered merchant ID. Aliases/aggregators must not be assigned different identities for the same source. Disabling preserves historical evidence.
- PUT `/{id}/mapping` is additionally super-admin only. It accepts `requestId`, `_version` (zero on create), textual `productId`, textual `variationId` (zero for a simple product), exact source `sku`, local `product` and boolean `active`. The connection/product/variation tuple is unique. Active mappings require an ordinary active physical warehouse product belonging to the connection's client. Foreign keys prevent deletion of referenced products; changing a mapping does not rewrite an accepted order.
- POST `/{id}/inbox/{item}/review` requires review permission. It takes no business overrides. It re-reads the paid processing order, corresponding simple products or variable parent/variation, fulfillment collection and then the order again. Product identities, SKU, published status, virtual/shipping flags and unsupported advanced metadata are checked. Virtual lines are excluded from physical quantities. Any existing fulfillment object blocks acceptance, including an unfulfilled draft. CORE requires a successful empty collection; LEGACY_METADATA only permits the specific `404 rest_no_route` response, consistent with a disabled core feature. Other errors fail. Custom plugin shipping fields still need actual-store acceptance.
- A successful review returns `ready`, `issues`, optional warehouse-validation explanation, exact source data, per-line physical/mapping results, combined `warehouseLines` and a `reviewHash`. The hash includes the inbox and connection revisions, authority version, mapping versions, local product/client/warehouse/channel versions and provider evidence. Source/client currency mismatch is held, with no implicit exchange conversion. Orders before the fixed source cutover require the separate historical migration workflow.
- POST `/{id}/inbox/{item}/accept` requires accept permission and `{requestId,reviewHash}`. It repeats the live read, locks and rechecks current local inputs, validates the approved hash, then atomically writes the warehouse order, references, immutable source evidence/link, audit and request journal. There is one order per inbox and per source identity/external order ID. A completed replay returns the original order without another provider read. Another valid request for an already accepted inbox also returns the same order; it cannot re-import a cancelled warehouse task.
- Accepted orders use `source=WOOCOMMERCE`, `workflow=JAVA_WOO_V1`, `shippingMode=INTEGRATION`, a source-qualified warehouse reference, original source reference/ID and mandatory scans. Acceptance does not reserve stock or assess warehouse fees. Allocation, pick confirmation, packing and release from hold recheck the provider and original source fingerprint. Individual barcode scans stay local with current authorization and enabled-source checks. Current account, role and scope checks use locking reads before committing, rather than a previous MySQL consistent-read snapshot. Source configuration leases remain held until the warehouse transaction finishes. Currency changes also block forward work.
- Ordinary manual editing and despatch cannot operate on a source order. Local cancellation releases reservations and retains history; it does not cancel/refund the external order. Carrier dispatch, feedback/outbox processing, inventory synchronization, source amendments, advanced product/order workflows and live account validation remain unfinished.
- POST `/{id}/resolve` requires query permission plus the original action permission and scope, and super-admin status for configuration. It accepts `{kind:authority|mapping|accept,item?,payload:<original input>}` for the current actor's request. Under the same connection lock it returns a committed result, or persists `requestCancelled=true` in the original journal slot. A late original request is then rejected as `ORIGINAL_REQUEST_CANCELLED`. Retrying resolution is idempotent. Raw database failures return a generic 500 without SQL or `committed=false`, because a connection/commit failure may have an unknown result; retain and resolve the original request.
